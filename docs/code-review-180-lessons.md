### F1 — P2：離線下載與播放共用 3,000 筆淘汰快取，會刪除已下載音檔

- **位置**：`vite.config.ts:61–65`，尤其 `maxEntries: 3000`；`app/lib/offlineAudio.ts:26–29,31–43`；`app/components/SceneListening.tsx:18–25`。
- **觸發條件**：下載大量課程後，累計讀取超過 3,000 個不同音檔。通用聽解的「全部課程」現有 6,300 個唯一音檔，頁面下載與 Workbox CacheFirst 使用相同 `lesson-audio-v5`。下載直接寫 Cache API，不會一開始就全部登記到 Workbox expiration metadata；之後讀取會更新 metadata 並觸發淘汰。因此「一次下載 6,300 檔就立刻只剩 3,000」並非本次證據所支持的說法。
- **最小重現**：以目前正式 base path build 啟動隔離瀏覽器，等待 SW 接管；在該 origin 的 `lesson-audio-v5` 寫入 3,002 個不同 `/audio/review-synthetic/<n>.mp3` 回應，內容為合成位元組，帶 `audio/mpeg` 與當前 Date。依序 fetch 這些網址，等待 expiration 非同步工作，再讀取最後一筆並等待完成。這會實際經過產出的 SW，沒有直接呼叫或改寫其淘汰邏輯。
- **預期／實際**：明確下載供離線使用的檔案應依產品的保留政策維持可用；實測初始 3,002 筆，讀取後只剩 3,000 筆，第 0 筆已不存在，最後一筆仍在。這不是磁碟 quota 驅逐，也不是一年到期，而是應用程式自己的筆數上限。之後斷網存取被移除的檔案會缺少快取，必須重新連線下載。下載區域已掛載時的計數也不會因背景淘汰自動更新。
- **證據與來源**：隔離 Chromium 使用目前生成的 worker 重現 `initial=3002, remaining=3000, firstStillCached=false, lastStillCached=true`。Workbox 的 `cachedResponseWillBeUsed` 會更新時間並執行 expiration；頁面下載的 cacheName 與 runtime route 一致。這是合成快取淘汰驗證，不宣稱播放了 3,002 個真實音檔。另以第 180 課實際 35 檔確認小量下載後斷網重載／播放正常。
- **是否本期引入**：否。起點 `16b4189` 的設定已為 3,000；當時通用課程為 2,100 檔，跨類別也已有累計超限可能。本期擴充至 6,300 檔，使單一通用課程的全部下載與保留策略明顯不相容。
- **建議方向**：區分明確下載的保留檔與可淘汰的播放快取，或制定能涵蓋完整下載集合的容量政策；保留 Range 支援、同 origin 與內容型別驗證。不要只把背景音檔數算入首次載入或 precache 上限，也不要直接無界限取消所有儲存管理。
- **必要驗證**：在隔離資料下下載完整集合、讀取超過 3,000 個唯一音檔，再斷網重載並讀取最早／最新檔；跨類別、SW 更新、重複下載／補抓、儲存不足與清除快取均需驗證。若採多個 cache，需驗證讀取路由確實能找到明確下載的檔案。

### F2 — P2：新版 worker 清除舊 chunk 後，選擇稍後更新的舊頁面無法載入課程

- **位置**：`vite.config.ts:13` 的 `registerType: 'autoUpdate'`；`app/useSwUpdate.ts:17–22,44–45`；`app/App.tsx:166–175` 的更新提示與「稍後」；動態教材網址由 `scripts/curriculum-chunks.mjs:74–78,88–94` 產生。
- **觸發條件**：開著舊版頁面時部署新版，等待新版 SW 自動接管；頁面仍執行舊入口，尚未 import 的課程 chunk 已換雜湊。使用者暫不重新載入，再進入該課程。靜態站只提供新版產物時，舊雜湊檔已不在站上。
- **最小重現**：分別建置起點 `16b4189` 與終點 `4ac67a3`，使用相同 origin 與 `/nihongo-lab/` 路徑。先服務起點、開首頁並確認舊 SW 控制頁面，尚不進入第一課；將伺服器切至終點、呼叫 registration.update()，等待頁面出現更新提示但不重載；前往 `#/lesson/general-listening-01`。
- **預期／實際**：若提供「稍後」，舊頁面應能維持有效教材載入，或在安全時機明確處理版本切換。實際請求 `assets/general-listening-01-B6EAP90o.js` 得到 404，畫面變為教材載入失敗；原本預先快取的舊 chunk 已無法供應。重新載入頁面後，第 01 課可正常顯示，未觀察到進度遺失。這不是永久不可恢復，也不是新 worker 安裝失敗。
- **證據與來源**：以兩個實際 Git 版本產物、同 origin 切換重現；記錄到舊 chunk 404、頁面錯誤與重載後恢復。生成的 worker 使用 skipWaiting／clientsClaim，precache activation 清理不再需要的舊資產；更新 hook 只設提示，dismiss 只隱藏提示，沒有延後啟用或保留舊 chunk。錯誤有顯示，並未被當作空資料成功。
- **是否本期引入**：根因不是本期新增。起點已有 autoUpdate、動態教材與稍後提示；本期序列化使大量既有 payload 重新產生雜湊，實際跨版本審查確認此風險仍存在。不是要求撤回容量優化。
- **建議方向**：協調 SW 啟用與頁面切版，例如保留等待狀態直到使用者可安全重載，或提供確實能維持舊頁面的資產版本保留策略。避免在未保存輸入時強制重載；如採 import 失敗復原，應限制重試次數，避免無限重新載入。
- **必要驗證**：兩版正式路徑產物測試「立即更新／稍後／繼續作答／切到未載入課程／多分頁／背景回前景／斷網」；確認進度與聽寫輸入的保存策略，以及所有 UI、lesson、category chunk 的相容性。不能只用更新節流的純函式測試取代跨版測試。

- JSON 正規化與純量共用沒有把陣列改成集合；packed index 透過位置還原，保留 ID 重複項與分類。own 特殊鍵採 computed key，factory／spread 仍產生獨立記錄。對目前教材及已測合成輸入，沒有發現內容、型別、順序或別名變更。
- 原始 ruby-notes 的純文字項目仍保留作者審閱作用，只在 payload 排除沒有實際注音的項目；實際注音有與完整 notes index 對照。非同步載入先註冊 notes 再提供資料，已載入元件透過訂閱更新。

- 六階段是通用課程內的學習路線，並非增加六個 app stage。分組由實際課數推導；既有網址與返回測試通過。現行課內沒有上一／下一課按鈕，依清單導覽；不能把未存在的按鈕當成測試通過。180 課完成訊息須課數與全部 audioReady 同時成立，沒有自動導向 181。

## 可選重構與後續驗證改善

這些項目不計入正式缺陷：

1. 可用單一作者登錄結構衍生 import／stage 登錄檢查，降低新增課程維護兩處的負擔；仍應保留唯一公開入口與靜態可分析的 build 邊界。
2. serializer 的 strings、paths、keys、shape、tail、ruby 成本估算存在交互作用。現行往返與最終 build 門檻能核實正確性／容量；並不保證每種未來資料都能省空間。若再優化，應保留真正 ESM／鍵序／修改獨立性與原 build budget 的驗證。
3. F1、F2 修正時需要瀏覽器整合回歸。現行 offline 的假 store 測試與 sw-update 的節流測試無法捕捉 Workbox 實際淘汰、跨版舊 chunk 清除；這解釋既有綠燈為何沒有排除兩項發現，不另重複列測試風格 bug。
4. 動態 import 重試文案／開發註解應明確區分 Promise loader 重試與瀏覽器同文件模組失敗快取；已有重載入口可恢復，不應宣稱同頁導航保證重試成功。
